# Application Site Visual Contract

This document defines the current visual contract for medication application site illustrations in EMControle.

It is intended for designers, SVG authors, image generation tools, and future Flutter implementation work. It documents current IDs and assets as they exist in code. It does not change app behavior.

## Scope

The current app has two kinds of application points:

- Explicit catalog points: fixed `ApplicationPoint` entries declared in the medication catalog.
- Generated protocol points: points generated by `ApplicationRotationService` from `MedicationApplicationProtocol.regions` when a medication has no explicit `applicationPoints`.

The UI currently renders `ApplicationPoint.imageAssetPath` as a static SVG. `highlightAreaId` exists in the model but is not applied dynamically yet.

## Current Model

### Domain Types

- `ApplicationSite`: broad legacy site entry with `id`, `label`, `bodyRegion`, `side`, `imageAssetPath`, and optional `regionId`.
- `ApplicationPoint`: user-facing point with `id`, `order`, `label`, `bodyRegion`, `side`, `parentSiteLabel`, `imageAssetPath`, `highlightAreaId`, optional `regionId`, optional `subRegionId`, optional `regionType`, and optional `bodySide`.
- `Region`: anatomical region with `id`, `label`, `type`, `side`, `svgAssetPath`, and `svgElementId`.
- `SubRegion`: anatomical subdivision with `id`, `regionId`, `label`, `svgElementId`, optional `order`, and optional `helperText`.
- `MedicationApplicationProtocol`: medication-specific visual and rotation protocol.

### Rotation Engine Behavior

- Oral and infusion medications produce no application points.
- If a medication has explicit `applicationPoints`, those are used directly.
- If a medication has no explicit `applicationPoints`, points are generated from `applicationProtocol.regions`.
- Generated point IDs follow:

```text
{medication.id}_{region.id}_point
```

- Generated labels follow:

```text
Local {index + 1}
```

- Generated `imageAssetPath` comes from `Region.svgAssetPath`.
- Generated `highlightAreaId` comes from `Region.svgElementId`.

## Issues Found

### Duplicate or Shared Application Point IDs

- Copaxone 20 mg and Copaxone 40 mg intentionally share the same explicit point IDs, such as `copaxone_abdomen_01`.
- There are no duplicate point IDs within a single medication's rotation list.
- Shared IDs across Copaxone presentations are acceptable because both presentations use the same visual site contract. If future behavior differs by presentation, IDs should become presentation-specific.

### Inconsistent Region Naming

Current region/site IDs mix direction placement:

- `right_thigh` and `left_thigh`
- `thigh_right_upper`, `thigh_left_upper`

This is internally workable but inconsistent. Prefer preserving current IDs for compatibility and using `thigh_right_*` only for subregion/highlight IDs.

### Shared Hip Assets For Glute/Hip Labels

- `glute_hip_right` uses `assets/images/application_sites/right_hip_region.png`.
- `glute_hip_left` uses `assets/images/application_sites/left_hip_region.png`.

If the product wants to distinguish gluteal/upper outer buttock guidance from hip guidance more precisely, create dedicated assets in a separate migration.

### UI Label and SVG Numbering Mismatch Risk

- Copaxone detailed SVG assets now expose one internal ID per contracted point marker.
- The current Copaxone SVG assets show orange markers but do not encode visible point numbers in the SVG source. The UI label remains the source of the `Local N` numbering.
- If future assets show multiple markers within one illustration, each visible marker must remain uniquely highlightable by ID or be clearly numbered according to the catalog order.
- Generated region-level points for Rebif, Betaferon, Plegridy, and Kesimpta use `Local N` labels, but their PNGs are broad region illustrations, not numbered point maps. This is acceptable only for broad-region guidance; it is not yet detailed subregion guidance.

### Dynamic Highlight Rendering Gap

`ApplicationPoint.highlightAreaId` is populated and references existing SVG element IDs, but the UI does not yet parse or style SVG internals. Application-site illustrations are still displayed as static assets.

## Recommended Region and SubRegion Structure

The recommended structure is:

```text
Medication
  MedicationApplicationProtocol
    Region[]
      id
      label
      type
      side
      svgAssetPath
      svgElementId
    SubRegion[]
      id
      regionId
      label
      svgElementId
```

Rules:

- A `Region.id` identifies an anatomical area.
- A `SubRegion.id` identifies a smaller target within a region.
- `ApplicationPoint.highlightAreaId` must match either a `Region.svgElementId` or `SubRegion.svgElementId`.
- For SVG assets, every `highlightAreaId` must exist as an internal SVG element ID in the referenced asset.
- For PNG assets, the asset file must exist and `highlightAreaId` must remain non-empty.
- Avonex must remain limited to:
  - right thigh
  - left thigh
- Copaxone may use detailed subregions.
- Rebif, Betaferon, Plegridy, and Kesimpta currently use broad generated region points. They may gain detailed subregions later, but that should be done through a dedicated spec and migration plan.

## Designer Asset Requirements

Each application-site SVG should:

- Be original artwork, not copied from medication leaflets.
- Include stable internal IDs for every highlightable region/subregion.
- Keep non-highlight anatomy in neutral tones.
- Put highlightable shapes in separate elements, not merged paths.
- Allow one active highlight, multiple historical highlights, or heatmap opacity changes.
- Keep labels/numbers visually consistent with `Local N` ordering when the asset shows multiple points.
- Avoid changing existing point IDs unless a migration spec is created.
